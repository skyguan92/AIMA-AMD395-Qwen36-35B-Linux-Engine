## 已确认并修复的引擎问题

1. **失败次数按整段历史累加，导致修复后仍被误拦截。**
   旧实现对“函数名 + 规范化 JSON 参数”的失败/空结果累计次数进行限流，
   两次失败后即使有成功修改，也永久阻止相同验证命令。新实现保留累计指标，
   同时按最近已完成工具进展计算当前失败窗口。成功修复后允许重新验证；
   不同命令明确返回零退出码时，即使没有 stdout，也可以构成状态变化。
   相同的无输出调用仍保持原有重试上限。

2. **全部调用被拦截，却返回正常完成。**
   旧接口可能只剩“我来检查”的正文或空消息，并带普通 `stop` 结束标记。
   新接口返回 `tool_call_no_progress`：非流式为 HTTP 400；流式为明确的 SSE
   error 后接 `[DONE]`，不发送成功的终止 `finish_reason`。
   仍有其他可执行调用时保留这些调用，不把整个响应一并丢弃。

3. **重放与并行顺序防护。**
   重复的 tool result ID 会被拒绝，防止虚增失败次数或将旧结果当作新进展。
   窗口按调用发起的 assistant turn 排序，迟到的旧结果不清除新的失败；
   同一批并行结果的到达顺序不改变决策。用户说“继续”、模型声称已修复、
   尚未完成的调用和失败的修复均不会重置窗口。

协议细节及新增 `history_no_progress_streak` 指标见 [API.md](API.md)。

## 边界与后续复测

### 两份文档的读取与格式校验

两份伪 DOCX 已成功读取并转存为私有 Markdown，对应 vLLM 的两份真正 DOCX
也提取为纯文本供对照。AIMA 会话记录中的 `write_file` 参数与原文件正文一致：
工具仅报告写入了 11,673 / 6,302 个字符，没有执行 DOCX 生成或格式验证。
这证明是直接写入文本的工具使用问题，而不是解压、Word 打开或字符编码失败。

新增开发辅助脚本（不成为便携原生引擎的 Python 依赖）：

```bash
python3 scripts/check-agent-documents.py report.docx evidence.docx
python3 scripts/check-agent-documents.py report.docx --markdown-dir recovered-text
```

脚本检查文件存在性、ZIP 完整性、OOXML 内容类型、主文档关系及 XML 结构；
缺少任一要求或以文本伪装 DOCX 时返回非零退出码 `2`。
可读文本会另存为 Markdown，绝不覆盖输入或已存在的转换稿；
**成功转成 Markdown 不会将不合格 DOCX 标为通过**。
真正 DOCX 的转换仅保留正文文本，不保留图片、样式、自动编号或版面。
本机指定的 Office artifact runtime 不可用，因此使用标准库进行有界 ZIP/XML 文本提取。

原反馈的两个 AIMA 文件均被正确判为不合格（退出码 2），两个 vLLM 对照文件通过
容器检查（退出码 0）。新增回归覆盖伪文件、真实容器、缺少关键部件、空/损坏文件、
不安全压缩成员和已有转换稿保护。

上层 Agent 应将这个检查作为工具执行步骤：生成脚本 → 实际运行 → 检查**全部**
目标文件 → 将检查结果作为 tool result 回传；失败后继续修复，全部通过后才宣布交付。
原生引擎不访问调用方的文件系统，不能仅凭 `write_file` 名称判断任意自定义工具的
二进制编码行为，所以不对所有同名工具硬编码拦截或擅自修改客户端提示词。
要阻止原有 Agent 再次交付伪文件，需要调用方接入此验证；发布说明不会把该辅助检查
宣称为原生引擎自动修复了 DOCX 内容或完成了原始 Agent 端到端复测。

本补丁不改变模型权重、GPU 数学路径、缓存、默认 thinking 模式或客户端的总工具预算。
它不会将 Markdown 自动转换为 DOCX，也不能从工具的“写入成功”推断文件格式正确或任务完成。
调用方仍需实际运行生成脚本，并检查所有目标文件的格式和内容后才能宣布完成。
